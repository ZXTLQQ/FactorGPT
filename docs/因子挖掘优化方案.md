## 二、诊断：七个瓶颈（按 ROI 排序）

### P0-1 搜索期没有独立的确认集 —— 最大的方法论漏洞

**证据**：`gridminer.py:380-478` 全流程在同一个 `panel` 上跑；筛选分（`:286`）用全样本 `RankIC` 均值；最终 `top_k` 的四维评价（`:468-473`）依然在同一段数据上。
对比之下，多尺度 GP 主线**是**分段训练的（`triage.py:242 split_panels_by_time` → `multiscale_mine`，report 里明确"样本外段仅在最后用于复核"）。同一项目里两条主线口径不一致。

**后果**：8 000 条候选、门槛 `|IC|≥0.01`（`:90`），纯噪声也能稳定跑出几条"显著"因子。`significance.py` 的 Sidak/FDR 是**事后**校正，校正的是 p 值，不是"这条因子是被同一段数据挑出来的"这一事实——选择偏差无法靠事后校正消掉。

**改法**
1. 在 `PanelData` 上按时间切三段：`search`（搜索与筛选）/ `confirm`（一次性复核）/ `live`（可选，模拟上线）。
2. 所有筛选、分层、早停只看 `search`；`confirm` 段在整个搜索结束后对 `top_k` 开一次封，且**不允许**因为 confirm 结果回头改搜索（改了就作废）。
3. 筛选分从"全样本 IC 均值"换成"分段一致性"：`score = |mean(IC_seg)| / (1 + std(IC_seg)/|mean|)`，或直接用**最差段 IC**（`evaluator.py:296 segmented_ic` 已有实现）。这一步比切分本身更能杀掉噪声因子。
4. 报告里给出 IS/OOS 衰减率 `decay = 1 − IC_confirm / IC_search`，与 `significance.py` 的 FDR 一起并列展示。

**验收**：固定种子下，top20 在 confirm 段 `IC>0` 的占比 ≥ 80%，且平均 `|decay|` 相对基线显著下降（**基线必须先测**，见第四节）。

**风险**：可用样本变短（约损失 20~30% 时间跨度）。缓解：小样本场景退化为 `n_segments` 分段一致性 + bootstrap，不做硬切分。

---

### P0-2 搜索期没有"增量"约束 —— 挖出一堆同一个因子

**证据**：`gridminer.py:467-473` 逐个把已评价因子塞进 `pool`，`incremental_ic` **只在最终 top_k 用**；搜索期的相关性剪枝（`:417-431`）是"与已入选者 |ρ|>0.95 就砍"的事后剔除，只和 top-8 比（`prune_corr_k=8`）。

**后果**：淘汰是"二元的"，且发生在求值之后——预算已经花掉了。真正想要的是**每选入一条，剩下的候选就对它正交化**，让搜索朝"尚未被解释的方向"走（即逐步正交匹配追踪 / 贪残差搜索）。

**改法**
1. 把 `incremental_ic` 前移到搜索期：维护一个"当前已选池的复合信号"，候选的适应度改为**对复合信号正交化后的残差 IC**（残差化是截面回归取残差，`panel.py:235 residualize_cs` 已有）。
2. 相关性剪枝从"淘汰"改为"降权"：`|ρ|>0.7` 不直接砍，而是按比例衰减其筛选分，避免误杀同源但更强的表达。
3. 剪枝比对对象从 top-8 扩到全部 `kept`，但用**低成本签名**先粗筛（见 P1-5）。

**验收**：产出因子池的两两平均 `|ρ|` 明显下降（当前需先测基线；目标 < 0.5），且复合因子的 IC 高于"最优单因子 IC"。

---

### P1-3 预算是均匀撒的 —— 8 000 条里有大量无效方向

**证据**：`gridminer.py:390-392`，候选生成量超预算时用 `self._rng.choice(..., replace=False)` **均匀无放回抽样**。层内先全量展开再抽样，等于"随机丢掉 3/4 的候选"，与哪类算子更有希望完全无关。

**改法**
1. 把候选按**算子族**分组（`unary / cs / ts / ts2 / bin / cs2 / neutral`），维护每族的"产出率"统计量（已求值数 → 通过筛选数 → 平均筛选分）。
2. 下一层按 **UCB**（均值 + 探索项）或 Thompson 采样分配预算比例；族内再随机。 warm-up 第一层保持均匀。
3. 更激进的版本：直接用已有的 `method_hub.bayesian_tpe_search` 在"算子族 × 窗口 × 层深"的离散-连续混合空间上做 TPE 采样（已实现且验证收敛）。

**验收**：同预算（8 000 条）下，top20 的平均四维得分提升；或达到同样得分所需预算下降。

**风险**：自适应会引入新的超参（探索系数）。建议先在固定随机种子下做 A/B，把探索系数写进 `SearchConfig` 落盘，保证可复现。

---

### P1-4 没有跨任务的记忆 —— 每次挖掘都从零开始

**证据**：`gridminer.py:241 _base_nodes` 的种子只有 registry 原始字段 + 用户传入表达式；`self._seen` 是**单次搜索内**的去重字典，进程结束即失忆。

**改法**
1. 建一个**因子基因库**：持久化 `node.key()` →（表达式、IC、ICIR、覆盖率、所属算子族、数据指纹）。用 SQLite 或 parquet 落 `data/factor_genome.*`（注意 `.gitignore` 里 `data/*.jsonl` 被忽略，用别的后缀或显式放行）。
2. 下次挖掘时，按"当前面板数据指纹 + 相似度"取 top-N 优质**子树**（不只是整条表达式）注入 `seeds`。
3. 统计高频优质骨架（如 `ts_std(ts_mean(x, w1), w2)` 这类模式），形成**结构先验**，在候选生成时优先展开这些骨架的参数变体。

**验收**：同一批数据连续挖第二轮，达到同等 top20 质量所需预算下降（这是"越挖越快"的唯一可量化证明）。

---

### P1-5 相关性剪枝太贵 —— 每条候选都跑全面板 IC

**证据**：`gridminer.py:419-421`，每个通过筛选的候选都要与 top-8 逐个算 `rank_ic`（O(T·N) 全面板）。在 8 000 条预算下这是纯浪费。

**改法**
1. 为每个已入选因子预计算一个**低维签名**：例如按 8~16 个时间块的 IC 向量、或对因子值做随机投影后的哈希。粗筛用签名距离，只有疑似相关的才做精算。
2. 签名随 `kept` 增量维护，避免重复计算。

**验收**：搜索墙钟时间下降，且最终池相关性指标不劣化。

---

### P1-6 两条主线不通信 —— LLM 与符号搜索各挖各的

**证据**：`agent/nodes.py` 产出的是 **Python 代码**，走沙箱 + 回测 + 反思；`mining/gridminer.py` 产出的是 **DSL 表达式树**。二者无交集：LLM 挖出的因子不会变成网格搜索的种子，网格搜索挖出的因子也不会交给 LLM 解释（上一轮的 `deep_analysis` 目前也是显式调用，未自动挂到 Agent 结果上）。

**改法**（双向桥）
1. **LLM → DSL**：对 LLM 生成的代码做静态分析（`ast`），把 `groupby('symbol')[...].rolling(w).mean()` 这类**可识别模式**翻译成 DSL 子树，作为 `seeds` 喂给 `gridminer` 做**局部精修**（换窗口、换算子、中性化）。翻译不了的整条保留为"黑盒因子"，仍可参与组合。
2. **DSL → LLM**：`expr.render()` 已有，把表达式渲染成可读公式 + 统计体检，交给 LLM 做**命名、经济学归因、失效场景分析**（`agent/interpret.py` 已有说明卡机制，直接复用）。
3. 在 Agent 的 `finalize` 前自动挂一次 `deep_analysis`，让两条主线的产出走同一份报告模板。

**验收**：LLM 提出的因子经 DSL 精修后，IC/ICIR 不低于原版；所有交付因子都带归因说明。

**风险**：代码→DSL 的翻译是**有损**的，必须保留"翻译失败"路径，不能让主线依赖它。

---

### P1-7 只学成功、不学失败 —— 同类错误反复发生

**证据**：`nodes.py:470 learn_factor` 开头即 `if not state.get("validation_ok"): return {}`——只有跑通的因子入库。而 `validate_and_compute`（`:255-266`）里的修复提示是**硬编码**的（SVD/NaN/除零那几条）。

**改法**
1. 建**失败模式库**：把 `validation_error` 按错误类型聚类（SVD 不收敛 / 前视 / 全 NaN / 除零 / 超时），记录触发它的代码片段特征。
2. 生成阶段（`_build_generate_prompt`，`:106`）把历史上**最高频的 3 条失败模式**作为负面约束注入，替代部分硬编码提示，让提示随使用自动演化。
3. 反思阶段传入"本次错误属于已见模式 #k，历史上有效的修法是 X"。

**验收**：同一账户连续 20 次挖掘，同类校验失败复发率下降。

## 三、其余候选（P2，视优先级取舍）

| 项 | 现状 | 改法 | 价值 |
|----|------|------|------|
| 筛选只用单期 horizon=5（`gridminer.py:84`，`evaluator.py:67` 的 `(1,5,20)` 只在最终评价算 decay） | 容易选中"只在 5 日上显著"的噪声 | 筛选分用多期复合（如 \|IC_5\| 与 \|IC_20\| 的几何均值或最小值） | 抑制短周期噪声 |
| 交易成本/容量/行业暴露只在评价期惩罚（`evaluator.py:74` 换手惩罚） | 搜索期完全不管能不能落地 | 搜索期加硬门槛（换手、容量、单行业暴露上限） | 挖出来的能直接用 |
| 搜索循环串行 | `_screen` 是 CPU 密集，numba 内核已 `nogil=True` | `ThreadPoolExecutor` 并行 `_screen`（numpy 计算时释放 GIL，线程有效） | 墙钟时间下降，改动小 |
| 四套搜索器并存（gridminer / multiscale_gp+specification_rl / genetic_factors / agent.rl_search） | 接口各异、无共享记忆 | 抽统一 `Searcher` 协议（`search(panel, budget, seeds, pool) -> SearchResult`），让 P1-4 的基因库对所有搜索器生效 | 维护成本，长期价值高但风险也高 |
| 文本因子是关键词词典（`unstructured_miner.py:30` 情感词典） | 颗粒度粗、覆盖有限 | 换嵌入 + 主题聚合（需引入模型依赖，见合规约束） | 差异化，但优先级低 |

## 四、落地顺序建议

**第 0 步（必须先做，否则无法证明优化有效）**
固定一个数据集 + 固定 `seed=42`，跑一次基线，记录并入库：
`IS IC / OOS IC / 衰减率 / top20 平均四维分 / 池内平均 |ρ| / 8 000 条墙钟时间 / 各类剪枝计数`。
建议做成 `scripts/mining_baseline.py`，以后每次优化都跟它比。

**第一步（P0-1 + P0-2）**：搜索/确认分段 + 增量信息前移。
理由：这两项**不增加算力**，只改变口径，直接决定产出的是"能用的因子"还是"过拟合的因子"。任何效率优化都应该在这之后做——否则只是更快地挖出垃圾。

**第二步（P1-3 + P1-5）**：自适应预算 + 剪枝加速。
理由：省下的预算正好补偿第一步切分损失的样本。

**第三步（P1-4 + P1-6 + P1-7）**：基因库、双线桥接、失败模式库。
理由：这三项共同构成"越用越聪明"的闭环，是"智能"二字的实质。

**第四步（P2）**：视前几步的实测结果决定是否需要。

## 五、明确不做

- **不重复实现**已在 `significance.py` / `evaluator.py` / `method_hub.py` 里有的统计方法（bootstrap、FDR、Shapley、TPE 等）——要复用而不是重写。
- **不引入新的大模型依赖**做文本因子（合规约束：现有数据源均为"个人研究、不可再分发"，另类数据接入需单独评估）。
- **不为了指标好看放宽** `min_ic` / `min_coverage` 门槛；要优化的是"每次求值的期望产出"，不是门槛。

## 六、需要你拍板的三件事

1. **确认集怎么切**：固定比例（如末 20%）还是滚动式（purged walk-forward，更严格但样本更短）？
2. **P1-6 的代码→DSL 翻译**是否要做？它是双向桥里唯一有风险的一环，不做也能靠"黑盒因子直接进组合"兜住。
3. **是否接受第一步带来的样本量损失**（约 20~30% 时间跨度），换取因子可信度？如果你的数据本身就不长（<2 年），建议改用分段一致性 + bootstrap 而非硬切分。
