## 二、逐项说明

### P0-1 时间切分（最关键的一处口径修正）

**问题**：生成、筛选、早停、四维评价全在同一个全样本上做，报告里的 IC 是
"挑完之后的 IC"。严谨的做法（留一段做 OOS）之前没做。

**做法**（`src/mining/split.py`）：按时间顺序把末段 `confirm_frac`（默认 25%）
封起来，搜索只在前面跑；搜索结束后在确认段上做 `n_confirm_folds` 个 purged
walk-forward 折叠复核。purge = `horizon`（默认 5 天），即 train 段末尾与 test
段起点至少隔开一个前瞻期，否则 train 最后一天的标签会用到 test 段的数据。

**不足两年就别硬切**（按你的要求）：样本 < 488 个交易日时 `SplitPlan.mode`
退化为 `soft`——不切分，改用分段一致性 + bootstrap 抑制过拟合，并在 UI 上把
原因写出来。这个退化是**自动**的，`split_mode` 可以强制 `split`/`soft`/`off`。

**复核结果不改搜索**：`_walk_forward_check` 只在 `run()` 末尾跑一次，结果回写到
报告的 `metrics`（`oos_ic_mean` / `oos_decay`）与 `detail.oos`，**不参与评分**。
如果拿复核结果回头改搜索，确认段就又变成了搜索段，OOS 数字立刻失去意义。

**验证**：80×600 合成面板上 IS IC −0.085 → OOS IC −0.056（衰减 35%，符号一致）。

### P0-2 增量信息前移

**问题**：新信息量只在最终评价阶段算一次，搜索期完全不看 → 选出来 8 条里
5 条是同一个动量的变体。

**做法**：候选通过 |IC| 门槛后，算两件事并取**更保守**的那个作为折扣系数：

1. `1 − |ρ(候选, 已选池复合)|`——直接度量"有多像已经选过的东西"；
2. `|残差 IC| / |原始 IC|`——对池复合做截面正交化后还剩多少预测力。

**为什么取更保守的那个**：RankIC 是秩相关，对尺度不敏感，"残差化后 IC 只掉
7%" 很常见（第一版只用了口径 2，实测平均折扣 0.93，等于没生效）。加上相关性
口径后池内相关性才真正降下来。

**顺带修的方向性 bug**：`segmented_ic` 的 `worst_seg_ic` 恒为 `np.min`，负 IC
因子的**最强**段会被当成最弱段，一致性恒等于 1。现在按 IC 方向取极值（正 IC
取最小段、负 IC 取最大段），反号段直接归零。

### P1-3 自适应预算

原来候选超预算时是"均匀随机丢掉 3/4"。现在按 (层, 算子族) 统计各族的筛选分
产出，用 UCB 分配配额（`budget_explore` 控制探索强度）。第一条没有历史的族靠
探索项保底，不会一开始就饿死。配额取整的余量/缺口用未选中候选补齐或截断，
**总条数严格等于预算**,所以可复现性不受影响。

### P1-5 剪枝加速

相关性剪枝对日期等距抽样（`prune_sample_step=4`）：横截面 IC 的天与天之间高度
冗余，抽 1/4 的天数把这部分开销降一个量级，排序结论不变。这是纯加速项，不改
结果。

### P1-4 因子基因库（默认关闭）

`src/mining/genome.py`：把每次搜索的优质候选按**表达式 key** 持久化到
`data/factor_genome.json`，下次挖掘作为种子注入，于是搜索能站在上次的肩膀上。

**默认关闭**是刻意的：注入种子会改变候选集，进而破坏"同种子同结果"的可复现
约定（`tests/test_mining.py` 里那条断言正盯着这个）。只有显式传 `genome=` 才
生效：

```python
from mining import gridminer as GM, genome as G
bank = G.GenomeBank()                      # 读 data/factor_genome.json
res = GM.mine(panel, config=cfg, genome=bank)   # 搜索前 warm start，搜索后写回
```

实测（80×600，max_expr=600）：第一轮产出 5 条基因，第二轮注入 5 条种子，
`bank.stats()` 显示 10 条 / 平均 |IC| 0.082。UI 的显著性检验页有开关。

### P1-6 双向桥

`src/mining/bridge.py`，把"LLM 写 Python"和"符号空间网格搜索"两条主线接起来：

* `code_to_expr` / `translate`：把 `alpha_factor(df)` 翻译成 DSL 子树。只认
  **高频可验证**的模式（`df.groupby('symbol')[c].transform(lambda x: x.rolling(w)
  .mean())`、`pct_change`、`shift`、numpy 一元函数、四则运算…），认不出就返回
  `None` 并给出原因与未匹配结构——绝不让主线依赖它成功。
* `expr_to_code`：把 DSL 渲染成可执行的 `alpha_factor`（含所需 helper 函数）。
* `expr_to_series`：执行上面生成的代码，用于等价性校验。

**实测**：内置 6 个模板因子 6/6 翻译成功（动量 = `ts_delay(ts_sum(ts_pct(close,1)
,20),1)` 等）；`ts_mean(ts_pct(close,1),10)` 的 DSL 求值与渲染代码执行结果
**相关系数 1.000000**。

**两个已知的坑，都写进代码注释了**：

1. `expr_to_code` 生成的代码**不过** `FactorSandbox` 的前视检查是故意的。DSL
   侧的因果性由 `expr.lookback` 与算子语义保证（t 日收盘可得的因子配 t+1 起的
   收益），而沙箱那条"价格列必须 shift(1)"的规则是为 LLM 自由代码准备的。两套
   口径不能互相套用，否则要么误报、要么把因子整体滞后一天。
2. NaN 边界有差异：pandas `rolling(20).std()` 要满 20 期，DSL 的 numba 实现用
   min_periods=1。语义一致（相关性 1.0），但前若干行一方有值一方是 NaN。

**接入**：`learn_factor` 入库时把代码翻译成符号表达式存进 `formula` 字段
（原来恒为空），于是 LLM 挖到的因子可以被符号搜索直接当种子复用。

### P1-7 失败模式库

`src/agent/failure_memory.py`。原来 `learn_factor` 只把**通过校验**的因子写进
学习库——Agent 只记得成功、不记得失败，同一类错误（前视、SVD 不收敛、整列 NaN、
超时）会一遍遍重犯；而 `validate_and_compute` 里那几条修复提示是硬编码的。

现在失败按**模式**聚类累计（7 类 + other），生成阶段把高频失败的修复提示作为
**负面约束**注入 prompt，于是提示词随使用自动长出来。落盘
`data/failure_memory.json`，库损坏时静默降级为空。

## 三、实测数字

`python scripts/mining_baseline.py --expr 1500 --topk 8 --seconds 300 --out data/mining_baseline_smoke.json`

```
metric                        legacy         new       delta
n_evaluated                     1500        1500       +0.0%
elapsed                      50.8500     40.5350      -20.3%
n_candidates                      12          12       +0.0%
is_abs_ic                     0.0934      0.0904       -3.1%
is_abs_icir                   0.9425      0.9233       -2.0%
pool_mean_abs_corr            0.5376      0.4298      -20.0%
confirm_oos_abs_ic            0.1148      0.0991      -13.7%
confirm_median_decay         -0.2675     -0.1621      +39.4%
confirm_sign_flip             0.0000      0.0000           -
```

**怎么读这张表**：

* 耗时 −20.3%，候选数持平 → 单位预算的产出上升。
* 池内平均 |相关| −20.0% → 选出来的因子确实是更不一样的因子，这是 P0-2 想要
  的（第一版只做残差口径时这项几乎没动）。
* IS 的 |IC| / |ICIR| 各降 2~3% → 这是**应当**发生的：搜索期不再奖励"再来一条
  动量"，单条因子看起来就没那么漂亮了。如果这项纹丝不动，说明折扣没生效。
* `confirm_oos_abs_ic` 那一行**不要用来比较优劣**：legacy 的确认段是它搜索时
  看过的（全样本搜索），所以它的 OOS 数字天然虚高。new 的 OOS 才是真样本外。
* `median_decay` 是负的（OOS 比 IS 还高），这不值得庆祝——合成面板上的因子是
  按构造稳定的，没有真实 alpha 衰减可供观察。**这套切分能证明的是"流程里确实
  有一段谁都没看过的样本"，不是"因子在真实数据上不衰减"**。真实数据上第一次
  跑出正衰减（预期 30~50%）才是这套东西真正开始说话的时候。

## 四、怎么用

```bash
# 基线对照（legacy vs new，固定种子）
python scripts/mining_baseline.py --expr 1500 --topk 8 --seconds 300

# 单次挖掘 + 样本外复核
python -c "import sys; sys.path.insert(0,'src'); \
from mining.panel import PanelData; from mining import gridminer as GM; \
r = GM.mine(PanelData.synthetic(80, 600)); \
print(r.split['mode'], r.oos['summary']); print(r.oos_table.head())"

# 代码 → DSL（翻译不了会给出原因）
python -c "import sys; sys.path.insert(0,'src'); from mining import bridge as B; \
print(B.translate(open('my_factor.py', encoding='utf-8').read()).to_dict())"
```

UI：智能挖掘 → 显著性检验页新增「启用因子基因库 warm start」开关；下方新增
「样本外复核」区块（衰减中位数、同号率、IS/OOS 对照表、反号告警）。

## 五、没做的 / 已知边界

1. **真实数据上的 OOS 还没跑过**。合成面板给不出 alpha 衰减，所以"新口径在真
   实数据上能把选择偏差压掉多少"目前只有流程保证、没有数字。建议第一次接真实
   行情时优先看 `oos_table` 的 `decay` 分布。
2. **bootstrap 只用于显著性检验，没用于筛选**。样本不足两年时我用的是"分段
   一致性 + 已有 bootstrap 检验"，没有另起一套筛选期 bootstrap——成本主要在
   每条候选都重采样，会明显吃掉预算，需要时再单开一项。
3. **DSL → LLM 归因只做了一半**：`expr_to_code` 能把符号因子渲染成代码给人/给
   LLM 看，但"自动调用 LLM 给挖掘因子命名、写经济学解释"还没有接进
   `finalize`。桥已经通了，接是半天的事。
4. **基因库不区分数据频率与标的池**，只按"标的数 + 时间跨度 + 字段集"的指纹
   匹配。跨数据集的通用骨架会被降级使用（排序靠后），但不会被拒。
5. 切分带来的 20~30% 时间跨度损失是**明账**：`n_search` 与 `n_confirm` 都写进
   `SplitPlan`，UI 上能看到，不是悄悄切的。
